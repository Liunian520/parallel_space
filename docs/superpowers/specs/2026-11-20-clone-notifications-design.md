# 分身通知页（方案 A）

基准：`main` `da50875f408bf5290b4e660f2c9641b54d35ea68`，已发布 1.3.41（versionCode 12341）。本文只定义下一轮实现。本文件落地时不改业务源码、不升版本、不打包、不上传。

已确认方案：设置里增加「分身通知」页。点一条通知只打开对应的虚拟分身，不发送原来的 `contentIntent`。

实现回合的版本目标是 1.3.42（versionCode 12342，arm64 分包仍按现有规则变成 14342）。那一轮再改 `pubspec.yaml`、`lib/config/app_version.dart`、`README.md` 徽章和 `CHANGELOG.md`。APK 只在打包机上构建。本规格不改 `update_manifest`。

常用分身分组不在本规格里。

## 目标

用户在 Alter Ego 里能看到虚拟分身此刻仍显示在系统里的通知，并可以打开对应分身，或只清除这一条。

页面回答三件事：

- 这条通知属于哪个虚拟分身
- 它的标题和正文是什么
- 用户可以打开那个分身，或只把这一条从系统通知栏清掉

列表的事实来源只有 `NotificationManager.getActiveNotifications()`。`files/clone_notification_index.json` 不能用来决定「还在不在」。

## 不在本功能里改的东西

- 启动图标和紫圈
- 默认分身的 `launchKey`，以及点名打开不改去默认分身
- 密码本、悬浮工具箱的只读行为、复制按钮位置、一键填入、`FLAG_NOT_FOCUSABLE`
- 机型适配检查 / 品牌权限状态页
- 配置备份版本 3，以及 `.aebak` 分身数据包
- 登录隔离的标识文件和开关
- 通知的投递格式。系统 tag、系统 id、渠道 id、分组 id、展示名和 `contentIntent` 都保持 1.3.35 的写法。本功能不改 `enqueue`、`decorate`、`cancelAll` 拦截，也不改删除分身时已有的 `cancelPosted`
- 不申请 `NotificationListenerService`，不增加「通知使用权」
- 不新建通知历史库。标题、正文、ticker 和 extras 不写入磁盘、不上传、不写入日志
- 不自动清除，也没有「全部清除」

## 入口

设置页 `lib/screens/settings_screen.dart` 的「工具箱与密码本」一节增加一行：

- 标题：`分身通知`
- 副标题：`查看虚拟分身正在显示的通知`
- 点击进入新页面，标题也是 `分身通知`

不放进悬浮工具箱。悬浮窗不加输入框，也不加这份列表。

页面顶部固定一句，无论列表空还是不空都在：

> 工作资料里的应用通知不在此列表。

列表为空时，另外显示：

> 现在没有正在显示的虚拟分身通知。

空列表不能写成「工作资料没有通知」。

支持下拉刷新。打开页面和下拉刷新做同一次读取。没有后台轮询，也没有新的常驻监听。

两次刷新里，先发出的结果后返回时丢掉，界面保持后一次的结果。页面销毁后返回的结果不 `setState`。读到的列表只活在这个页面的内存里，离开页面即丢。

## 读哪些通知

宿主进程调用 `NotificationManager.getActiveNotifications()`。应用最低是 Android 8（`minSdk` 至少 24），这个方法从 API 23 起就有，不需要通知使用权。它只返回本应用自己发出、用户还没划掉、应用也还没取消的通知。

一条通知进入列表，必须同时满足：

1. `StatusBarNotification.getTag()` 能按现有规则解析。规则与 `CloneNotificationPolicy` 的私有 `split` 相同：以 `ae1` 加分隔符 U+001F 开头，分成 5 段，依次是前缀、userId、包名、应用自己的 id、应用自己的 tag。userId 能解析成大于等于 0 的整数，包名非空。解析失败的条目丢掉，不显示成「当前没有这个分身」。
2. 系统这次确实返回了它。索引里有、这次读取没有的，不显示。

宿主自己的工具箱、虚拟定位和权限提醒 tag 不是 `ae1` 开头，自然不出现。

实现要在 `CloneNotificationPolicy` 上增加公开的解析函数，供列表和测试使用。它只读 tag，不读通知正文。现有 `systemTag`、`belongsTo`、`systemId` 的结果保持不变。

从 tag 得到包名和 userId 之后，分身身份用现有规则：

- userId 为 0：`w:包名`
- userId 大于 0：`w:包名#userId`

这就是 `CloneApp.uidFor`。不用 `launchKey`。

当前分身名单里有这个 uid：行上用那一份的 `customName`。没有：行上固定写 `当前没有这个分身`。不根据包名去猜一个还在的分身。

## 一行上有什么

每条系统通知一行。分组摘要和它的子通知如果都被系统返回，就是两行，不合并，也不藏起摘要。公开字段表明它是分组摘要时，该行带上 `分组摘要`；不是分组摘要时不带这四个字。

一行显示：

- 分身名，或 `当前没有这个分身`
- 通知标题。标题和正文都空时，显示 `这条通知没有标题`
- 通知正文，有则显示

标题和正文只来自这次读到的 `Notification`。不写入 `clone_notification_index.json`，不写入新文件，不放进备份。

排序：`getPostTime()` 新的在前；时间相同再按系统 tag 的 UTF-16 码元，然后按系统 id。

同一条通知被应用更新后，系统里仍是同一个 tag 和同一个系统 id，读取结果里只有最新的一条。

## 打开

只有对上当前分身名单的行可以打开。点击调用现有的 `launchVirtual(包名, userId)`，不新写一套启动，也不改默认分身的选择。

不调用这条通知的 `contentIntent.send()`，也不调用 `deleteIntent` 或动作按钮里的 `PendingIntent`。

打开失败时用现有的失败提示。不能因为失败再去发送 `contentIntent`。

`当前没有这个分身` 的行没有打开操作。

## 清除

每一行有单独的「清除」。没有「全部清除」，页面上也不调用 `NotificationManager.cancelAll()` 或任何 `cancelAll*`。

清除一条时：

1. 再次确认这条的系统 tag 能解析，并且 `belongsTo(系统 tag, 解析出的包名, 解析出的 userId)` 为真。不满足则不调用 `cancel`，提示清除失败。
2. 调用 `NotificationManager.cancel(系统 tag, 系统 id)`。系统 id 用 `StatusBarNotification.getId()`，不用应用自己的 id。
3. `cancel` 没有抛出时，如果索引里有这个系统 tag，只删索引中的这一条。不 `take` 掉整个分身的记录，也不删除其他分身的记录。

常驻通知也允许这一次 `cancel`。应用如果马上再发，下一次刷新会再看到它。本功能不循环清除。

清除之后重新读一次活跃列表，用同代际规则更新界面。

## 工作资料

工作资料里的应用不是 BlackBox 进程，通知不经过 `ae1` 改写，也不会出现在宿主这次 `getActiveNotifications()` 的结果里。

页面不把它们混进虚拟分身列表，也不为它们提供打开或清除。固定说明就是上面的「工作资料里的应用通知不在此列表。」

## 已知风险（写明，本功能不解决）

删除虚拟分身时，现有 `CloneNotificationCompat.cancelPosted` 会按索引取消那一份的通知。这个调用保持原样。

归属用的是包名加 userId。userId 会在删除后被下一份新建的分身复用，它不是 `launchKey`。如果上次 `cancel` 失败，残留的 `ae1` 通知仍带着旧的包名和 userId。新的那一份使用同一个 userId 时，这条残留会显示在新分身下面，打开也会打开新的这一份。

首期不改 tag、id、渠道或 `contentIntent`，所以这条风险没有被解决。实现不得把它写成已修复，也不得靠猜测把残留改挂到别的分身上。

另外三件现有行为保持可见：

- 分组摘要和子通知是两条记录
- 同一 tag 与系统 id 的更新覆盖成一条
- 常驻通知可以清除，应用可能立刻再发一条

Android 13 及以上，如果用户没有把通知权限给 Alter Ego，虚拟分身的通知发不出来，这一页可以是空的。空列表仍只用上面的两句固定文案。这不新增权限。页面不主动弹出通知授权窗。

小米、华为、荣耀、OPPO、vivo 等系统的通知栏可能折叠、延迟或不显示。`getActiveNotifications()` 的结果不必和状态栏逐条一致。本规格不把这种差异写成已对齐。

## 代码边界

实现可以改这些位置：

- `lib/screens/settings_screen.dart`：增加入口
- 新的分身通知页，以及只读的列表模型
- `lib/services/native_bridge.dart` 与对应 Kotlin：只增加读取活跃通知和单条清除
- `CloneNotificationPolicy`：公开解析 tag。现有 `systemTag`、`belongsTo`、`systemId` 的计算结果不变
- 单条清除成功后，按上面的规则更新已有索引中的一条。不改索引的文件格式
- 对应的 Java `main` 测试和 Flutter 测试

不改 `CloneNotificationCompat` 的投递、`contentIntent` 保留和 `cancelAll` 拦截。不改 `VaultStore`、默认分身、权限状态页、备份编解码和启动图标。

日志可以有包名、userId、条数和清除是否抛出。不写标题、正文、ticker、extras，也不写 `PendingIntent`。

## 自动化验收

实现同时满足下面各项才算完成。

**纯逻辑**

- `systemTag("com.a", 0, 7, "t")` 解析回包名 `com.a`、userId 0、应用 id 7、应用 tag `t`。userId 1 解析成 `w:com.a#1`，userId 0 解析成 `w:com.a`
- 不是 `ae1` 开头、段数不够、userId 不是非负整数、包名为空：解析失败，不进入列表
- 同一份活跃结果里，分组摘要和子通知都保留
- 索引里有而活跃结果里没有的 tag 不出现
- `belongsTo` 为假时，清除决策是不调用 `cancel`
- 决策函数没有 `cancelAll` 分支

**Flutter**

- 设置里能打开「分身通知」
- 空列表显示「现在没有正在显示的虚拟分身通知。」，并且同一页有「工作资料里的应用通知不在此列表。」
- 有通知时，工作资料那句仍在
- 对上分身的行可以打开；「当前没有这个分身」的行没有打开
- 先返回的旧刷新不覆盖后一次的结果

测试使用夹具，不读取本机真实通知，不上传通知内容。

**打包机和真机**

- Kotlin / Gradle 编译是否通过，只由打包机上的构建结论确定。云端没有 Android SDK 时，不得写成 Kotlin 已编译
- Java `main` 套件入口不是 JUnit
- 状态栏与本页是否一致，只在真机上看。本规格不把 HyperOS 或其他品牌写成已验收

## 验收

- 设置进入「分身通知」。打开和下拉都只读 `getActiveNotifications()`，只显示能解析成 `ae1` 且这次仍活跃的通知
- 索引文件不决定列表里有没有这条
- 点对上的行只打开该虚拟分身，不发送 `contentIntent`
- 每行可单独 `cancel(系统 tag, 系统 id)`，且先通过 `belongsTo`。没有全部清除，不调用 `cancelAll`
- 对不上当前分身的 `ae1` 通知仍显示为「当前没有这个分身」，只能清除，不能打开，也不自动清除
- 工作资料的说明固定存在。空列表的文案是「现在没有正在显示的虚拟分身通知。」
- 归属是包名加 userId。userId 复用导致残留通知挂到新分身的风险写在本文「已知风险」里，实现不把它标成已修复
- 不新加通知使用权，不新加历史库，不改投递格式、默认分身、密码本、权限状态页、备份和图标
- 上文自动化项有对应测试。OEM 状态栏没有被写成已对齐

## 已接受的限制

- 这一页是打开时的一张快照，加上用户主动的下拉刷新。离开页面后不保留标题和正文
- 工作资料通知不在这里，也不能从这里清除
- 原通知点击后会进哪个页面，仍由 1.3.35 留下的 `PendingIntent` 决定。本页的「打开」只启动那个虚拟分身
- 删除后 userId 被复用、且上次取消失败时，残留通知会挂到新分身。首期不改投递格式
- Android 8–16 各品牌的通知栏外观没有本功能的真机通过记录
