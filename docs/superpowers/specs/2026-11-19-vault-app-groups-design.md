# 密码工具箱按应用分段（方案 A）

基准：`main` `5107659d214e05f09b102f1caea01541e81e7498`，已发布 1.3.39（versionCode 12339）。本文只定义下一轮实现。本文件落地时不改业务源码、不升版本、不打包、不上传。

已批准方案：悬浮列表把全部可见账号按包名分段，分段标题不可点击。默认始终显示全部账号。主应用密码本维持按分身分组，搜索补上应用显示名和分身自定义名。

实现回合的版本目标是 1.3.40（versionCode 12340，arm64 分包仍按现有规则变成 14340）。那一轮再改 `pubspec.yaml`、`lib/config/app_version.dart`、`README.md` 徽章和 `CHANGELOG.md`。APK 只在打包机上构建。本规格不改 `update_manifest`。

## 目标

用户展开悬浮工具箱的密码本时：

- 看到每一条现有读取能返回的账号，每条只出现一次
- 这些账号按应用包名分成若干不可点击的标题，标题下面就是该包名的全部备注行
- 当前前台应用的那一段可以排在最前，其余段仍在列表里
- 点备注仍进入现在的详情，复制和一键填入的位置与行为保持原样

用户在主应用密码本里搜索时，除现有字段外，还能用应用显示名和该条账号所属分身的自定义名找到它。密码字段不参与匹配。

## 不在本功能里改的东西

- 启动图标和紫圈
- `filesDir/vault_plain.json` 的格式：版本号继续是 `2`，字段继续是 `id`、`pkg`、`clone`、`label`、`user`、`pass`、`note`。本功能不迁移、不重写、不补写空 `id` 或空 `pkg` 的旧记录，也不为保留未知字段去加一条写回
- 配置备份版本 3，以及 `.aebak` 分身数据包。密码本和 PIN 继续不进入这两份备份
- 主应用密码本的分组键。`groupVaultEntries` 继续「有分身 id 按分身，否则按包名」，当前分身段仍排在前面
- 悬浮详情里的账号行、密码行：复制按钮仍在各自右侧；底部仍是「一键填入」。`performFill`、`copyUser`、`copyPass` 不改
- 悬浮窗窗口标志：气泡和展开面板继续带 `FLAG_NOT_FOCUSABLE`。悬浮球、工具箱面板、密码本列表、详情、分段标题都不新增 `EditText`、`SearchView`、可编辑控件或会拉起输入法的焦点
- 生物识别和加密门槛。`VaultAuth.prompt` 继续直接返回 `ok`，列表继续 `locked: false`
- 默认分身、登录隔离、通知隔离、权限状态页、保活与无障碍常驻
- 分身详情「管理此分身账号」现在传入包名、新建时落到第一份 `w:包名` 的入口。本功能不改 `clone_detail_screen.dart` 这一处
- 悬浮窗现有的密码本刷新链路：进程内监听、`FileObserver`、`refreshVaultAsync` 的引用比较，以及 `appLabelCached` 在名称返回时 `requestRebuild("label_memo")`。本功能不修这条链路，也不再增加重建来源
- 搜索词不写入 `SharedPreferences`、密码本文件、备份或 Intent。页面 `State` 里的控制器可以继续只活在内存中，离开页面即丢

## 数据从哪来

悬浮列表和主应用列表的条目源都是现有 `VaultStore.list` / `vaultList`。解析时 `id` 或 `pkg` 为空的记录今天就不会进入这个列表。本功能把「可见列表」原样拿来分段和搜索，不另做一道过滤，也不把被解析丢掉的记录救回来。

可见记录里：

- `pkg` 是应用分段键，也是段的排序键
- `clone` 可以为空。空 `clone`、对不上现有分身、或包已从分身名单消失的记录，只要还在可见列表里，就留在它的 `pkg` 段内
- 没有名为「未关联」的收容段。可见记录必有非空 `pkg`，所以每条都能进入某个包名段
- 显示名、安装判断、搜索词都不是密码本字段。它们只存在于内存，不写回 JSON

因此本功能没有新的 `persist`、`upsert`、`delete` 或 `notifyChanged` 调用。未知 JSON 键不会因为本功能的写回而丢失；下一次用户自己的保存仍走现有 `persist`，那是既有行为，本功能不加自动写回去改变它。

## 悬浮列表

### 分段

`buildVault` 在账号非空时，用包名把可见记录分成段。一个包名一段，一段里的记录互不重复，所有段合起来等于全部可见记录。

段标题是现有风格的 `TextView`（沿用 `section()` 的字号和颜色）。不给标题设置点击、长按或 `setFocusable(true)`。`TextView` 默认不取得输入焦点。标题不折叠，段与段之间没有「只看这个应用」的开关。列表上方的说明保持现有这一句，N 仍是可见记录条数：`全部 N 个账号 · 点备注名查看 / 填入（不限当前分身）`。中间的点是 U+00B7，两侧各一个空格。

去掉现在的三段式标题「当前分身」「其他分身」「全部账号」。当前前台不再把别的应用从列表里拿掉。

记录为空时仍走现有 `emptyVault`：「还没有账号」，以及「去密码本添加」。这个空态只在可见记录为 0 时出现。本方案没有「某一段被筛空」的状态，因为没有筛选；没有记录的包名不生成标题。排序函数不删除输入。夹具里没有空包名。若调用方传入空包名，这条仍要出现，单独放在所有非空包名之后，标题全文为 `应用信息不可用`。

### 排序

排序键不用应用显示名，也不用备注行的回退标题（账号、分身名、包名）。异步补上的名称只改标题文字，不改变顺序。

段顺序：

1. 段的包名等于悬浮窗现有前台包名 `pkg` 的那一段排最前。前台包名为空，或没有任何记录属于它时，没有这段，其余段直接按包名排
2. 其余段按包名的 UTF-16 码元顺序升序，区分大小写，不用地区排序，也不用拼音。当前段若在码元顺序里本来就靠前，测试仍要另用一个码元顺序更靠后的前台包名来证明「当前段提前」生效

段内顺序：

1. 现有 `matchesInstance` 为真的记录排在前面。这个函数维持现状：`clone` 非空时，等于前台 `uid`，或在前台是该应用第一份（`userId == 0`）时等于前台包名；`clone` 为空时，仅当前台是第一份且 `entry.pkg` 等于前台包名
2. 然后按存储的备注名 `label` 的 UTF-16 码元顺序。空备注名排在非空备注名前面。不用 `remarkTitle`
3. 然后按 `id` 的 UTF-16 码元顺序。重名记录都保留，顺序由 `id` 固定

`remarkTitle` 仍只负责行上显示的主标题：备注名，空或「未命名」时回退账号，再回退分身名，再回退包名。回退结果不参与排序。

### 标题文字和安装判断

标题由纯函数根据包名和一次查找结果决定。查找结果只有四种，生产路径只会造出前三种：

| 查找结果 | 标题全文 | 何时使用 |
|---|---|---|
| `pending` | 包名 | 这次进程里还没有该包的查找结果 |
| `named`，且名称去空白后非空 | 该名称 | 包管理器返回了非空应用名 |
| `unavailable` | `包名 · 应用信息不可用` | 名称为空，或查找失败。`NameNotFoundException` 和其他异常都走这里 |
| `reliablyUninstalled` | `包名 · 未安装` | 只有调用方另行持有可靠的「已安装全集、其中确实没有这个包」时才能使用 |

本版本的可靠安装全集不存在。清单没有 `QUERY_ALL_PACKAGES`。桌面启动器查询会漏掉没有启动图标的已装应用。`getApplicationInfo` 抛出 `NameNotFoundException` 时，可能是未安装，也可能是 Android 11 起的包可见性让本应用看不到它。因此悬浮窗和主应用的查找适配层把 `NameNotFoundException`、其他异常、空名称一律收成 `unavailable`，不收成 `reliablyUninstalled`。

纯函数保留第四种结果，只为把「唯一允许写出未安装的输入」锁在测试里。`VaultAppHeading.java` 和 Dart 里的对应函数可以包含「未安装」这三个字，并且只能出现在 `reliablyUninstalled` 的返回值里。悬浮窗、通道适配和其他界面源码不写这三个字，也不把查找结果收成 `reliablyUninstalled`。用户能看到的标题因此不会出现「未安装」。

名称晚到时：

- 把结果写入现有内存备忘（按包名）。备忘不是密码本文件
- 若当前面板里仍有 `tag == 包名` 的标题 `TextView`，只对它 `setText` 成新的标题全文
- 不调用 `requestRebuild`、`rebuild`、`refreshVaultAsync`、`VaultStore.invalidateCache`
- 不因为名称变化而重排段或段内记录
- 若标题视图已经不在树上，只留备忘。下一次既有重建会读到备忘。在那之前标题可以继续显示包名。这是为了不新增重建源而接受的延迟，不另开一次重建去补

分段标题不走 `appLabelCached`。那个函数今天会在名称返回后 `requestRebuild("label_memo")`，行副标题仍用它。本功能不改那条路径；它继续可能在名称返回时重建列表面板。

### 详情身份

详情继续用内存中的 `vaultDetailId`，值是记录的 UUID。编辑保存沿用原 id。删除按 id。

既有刷新到达且面板展开时，详情按这个 id 重新查找：

- 找到：显示新内容，id 不变
- 找不到：现有文案「这条账号已删除或不存在」，以及「回到列表」

重名、改备注名、改所属包名都不更换 id。所属包名改变后，这条记录出现在新包名段里，仍是同一 id。

## 主应用搜索

密码本页的搜索框保留，仍是这个功能里唯一的文字输入。提示可以改成说明也能搜应用名和分身名，但输入框仍只在 `VaultScreen`。工具箱页、设置页、悬浮窗不加搜索框。

`filterVaultEntries(entries, query)` 的现有调用保持可用。新的名称表用可选参数传入。查询先 `trim` 再转小写；空查询返回原列表，顺序不变。

非空查询命中下面任一字段即保留该条（大小写不敏感的子串）：

- 备注名 `label`
- 账号 `user`
- 包名 `pkg`
- 备注 `note`
- 分身 id `clone`
- 应用显示名：该包名在同步表或异步表里的非空名称。同步表是分身名单里同包名每一份的 `appName`，有多份就都算。异步表来自下面的只读通道。两个表都算，异步响应不清除同步表
- 分身自定义名：`vaultEntryMatchesInstance` 对得上的每一份非空 `customName`。通常只有一份。对不上现有分身时，没有自定义名候选。对不上的那份自定义名不能让这条命中

函数不读取 `password`，也不把「应用信息不可用」「未安装」当作搜索词的特殊命中。查询词若本来就写在备注名、账号、包名、备注或分身 id 里，仍按那些字段命中。

名称通道：

- 方法名 `vaultAppLabels`
- 入参只有包名字符串列表。不传查询词、账号、备注、密码或整条记录
- 出参是每个包名的 `named` 或 `unavailable`，加上名称字符串。没有 `uninstalled`
- 只读包管理器。不写密码本，不写日志里的查询词、账号、备注或密码。通道本身没有查询词
- 页面拿到可见记录后，按其中的包名集合发起。键入搜索不重新发起
- 记录重新加载且包名集合变化时再发起一次

代际：每次发起把整数代际加一，响应对应该次的代际。返回时若页面已销毁，或代际不等于当前代际，丢弃整个响应，不合并进现有异步表。当前代际的响应整表替换异步表，然后由界面用**此刻**的 `_query` 重新调用 `filterVaultEntries`。不保存「某次查询的结果快照」，所以晚到的名称不会把列表冻在旧查询上。键入只改 `_query` 并立刻用已有的同步表和异步表重算，不增加代际。

同步的分身自定义名和 `appName` 不放进这个异步表，也不被异步响应清掉。

## 三个空态各说各的

三句现有文案都保留，触发条件互不替代：

| 条件 | 文案 |
|---|---|
| 悬浮列表或主应用列表的可见记录为 0，且主应用搜索框为空 | 还没有账号 |
| 主应用搜索框非空，过滤后为 0 | 没有匹配的账号 |
| 悬浮详情的 `vaultDetailId` 在最新可见列表中不存在 | 这条账号已删除或不存在 |

实现可以改这些位置：

- `lib/services/vault_group.dart`：包名分段排序、标题全文、搜索的可选名称参数。`groupVaultEntries` 的分组键不变
- `lib/screens/vault_screen.dart`：把名称表传入搜索；持有查询词和代际。分组调用仍是 `groupVaultEntries`
- `lib/services/native_bridge.dart` 与对应的 Kotlin 通道：只增加 `vaultAppLabels`
- `android/app/src/main/java/com/parallelspace/parallel_space/VaultAppHeading.java`：无 Android SDK 依赖的标题与排序纯函数
- `ToolboxOverlayService.buildVault`：改成按该纯函数分段；标题 `tag` 为包名；名称返回时只 `setText`
- `android/app/src/test/java/.../VaultAppHeadingTest.java`：`main` 入口，与现有 `CloneEnumPolicyTest` 一样，不是 JUnit
- `test/vault_test.dart` 或同目录新的 Dart 测试

`VaultStore.kt` 不改。`clone_detail_screen.dart` 的密码本入口不改。`registerVaultListener`、`startVaultFileObserver`、`refreshVaultAsync`、`appLabelCached` 的函数体不改。

Dart 与 Java 各有一份纯函数。下面这张夹具两边都必须得到同一结果。比较是 UTF-16 码元顺序：`乙`（U+4E59）在 `甲`（U+7532）前面。

夹具记录：

| id | pkg | clone | label | 调用方给出的「当前分身」 |
|---|---|---|---|---|
| b | com.z | w:com.z | 乙 | 否 |
| a | com.a | w:com.a#1 | 甲 | 是 |
| c | com.a | w:com.a | 甲 | 否 |
| d | com.a | w:com.a | 乙 | 否 |
| e | com.m | （空） | （空） | 否 |

调用方按上表传入「当前分身」布尔值，前台包名取 `com.z`（码元顺序在 `com.a` 之后）。段顺序必须是 `com.z`、`com.a`、`com.m`。`com.a` 段内顺序是 `a`、`d`、`c`：先当前分身，再备注名（`乙` 在 `甲` 前），再 id。五条都在，没有第六条。

前台包名为空，且五条的「当前分身」都传否。段顺序是 `com.a`、`com.m`、`com.z`。`com.a` 段内顺序是 `d`、`a`、`c`。

标题夹具：

| 输入 | 全文 |
|---|---|
| `pending`，包名 `com.qq` | `com.qq` |
| `named`，名称 `微信` | `微信` |
| `named`，名称为空白 | `com.qq · 应用信息不可用` |
| `unavailable` | `com.qq · 应用信息不可用` |
| `reliablyUninstalled` | `com.qq · 未安装` |

上表里的间隔点都是 U+00B7，点的两侧各一个空格。

搜索夹具一条记录：`label=主号`，`user=alice`，`note=宿舍`，`pkg=com.tencent.mm`，`clone=w:com.tencent.mm#1`，`pass` 为只出现在密码字段的 `p@ss-unique`。同步应用名 `微信`，该分身自定义名 `小号`，第一份分身自定义名 `大号`。

| 查询 | 结果 |
|---|---|
| 空 | 保留 |
| `alice`、`宿舍`、`com.tencent`、`w:com.tencent.mm#1`、`主号`、`微信`、`小号` | 命中 |
| `大号` | 不命中 |
| `p@ss-unique` | 不命中 |
| `应用信息不可用`、`未安装` | 不命中 |

另有一条旧记录：同包名、`clone` 为空、备注名不同。`大号` 能命中它（第一份分身），`小号` 不能。

代际夹具：当前代际是 2 时，响应代际 1 不应用；响应代际 2 应用。应用时参与过滤的查询词是应用时刻的查询词，不是发起时刻的查询词。

## 既有风险（写明，本功能不修）

- 分身详情「管理此分身账号」传入的是包名。从第二份及以后的分身进去新建，`clone` 会写成 `w:包名`，也就是第一份。按应用分段会把它和第一份放在同一段。段内谁算「当前分身」仍由现有 `matchesInstance` 决定。要让新建记到第二份，得改这个入口，那不是本功能
- 同一次保存会同时走到进程内监听和 `FileObserver`。`VaultStore.list` 每次返回新的列表对象，`old == list` 比的是引用，内容没变也会重建。展开的列表和详情都会重建。1 秒内重建超过 5 次会被现有风暴保护丢掉，面板可能短时间留着旧视图。重建会拆掉 `ScrollView`，滚动位置回到顶部。本功能不保存滚动位置，也不合并这两路刷新
- `appLabelCached` 仍会在行副标题的应用名返回时请求 `label_memo` 重建，从而再次把滚动打回顶部。分段标题自己的补名不走这条重建
- 标题视图若在补名完成前被上述既有重建换掉，而备忘又尚未写入，新标题会先显示包名，直到再下一次既有重建。补名回调只更新仍在树上的、tag 相符的标题，不为了这一拍去重建
- 生产路径无法可靠区分「未安装」和「包可见性不足」。用户会看到「应用信息不可用」，而不是「未安装」。已保存的账号仍在该包名段里
- 应用显示名相同的两个包名会有两段、两行相同的标题文字。段顺序仍按包名。本功能不把包名再写进已解析名称的标题
- 云端环境没有完成过本仓库 Kotlin 的发布编译。实现回合在云端跑通的 Dart 测试和 Java `main` 套件，不能写成 Kotlin 已编译通过，也不能写成 HyperOS 已验收

## 自动化验收

实现同时满足下面各项才算完成。

**纯逻辑（Dart 与 Java `main` 各一份，夹具与上文相同）**

- 五条夹具每条出现一次。前台包名 `com.z` 且布尔值按上表时，段顺序是 `com.z`、`com.a`、`com.m`，`com.a` 段内是 `a`、`d`、`c`。前台包名为空且布尔值全否时，段顺序是 `com.a`、`com.m`、`com.z`，`com.a` 段内是 `d`、`a`、`c`
- 输入里多一条空包名记录时，原五条顺序不变，空包名单独排在最后，标题全文是 `应用信息不可用`，该条不被删除
- 空 `clone`、不在分身名单中的包名仍在结果里
- 标题五种输入的全文与上表一致。`unavailable` 和空白 `named` 的全文里没有「未安装」

## 验收

- 悬浮密码本默认列出全部可见账号，每条一次，按包名分段，标题不可点击、不折叠、不筛选
- 当前应用的段可以在最前，其他段仍在；段内当前分身在前，其后按备注名和 id
- 名称异步补全不重排，也不新增 `requestRebuild` 来源
- `NameNotFoundException` 显示 `包名 · 应用信息不可用`。生产界面不出现「未安装」
- 主应用仍按分身分组。搜索在原有五个字段之外匹配应用显示名和所属分身自定义名，不匹配密码，不把查询词、账号、备注、密码写入日志或磁盘
- 旧代际的应用名响应不覆盖新结果；名称返回后按当时的查询词重算
- 三种空态文案和触发条件与上表一致
- 密码本 JSON 仍是 v2，本功能没有写回。配置备份仍是 v3，`.aebak` 不含密码本
- 复制按钮、一键填入、`FLAG_NOT_FOCUSABLE`、毛玻璃、生物识别缺省、图标紫圈、默认分身、隔离和权限页保持现状
- 上文「既有风险」里的分身详情入口和重复重建仍在，没有被本功能顺手改掉
- 上文自动化项有对应测试。HyperOS 与打包机 Kotlin 编译没有被写成已在云端通过

## 已接受的限制

- 账号很多时，悬浮列表靠滚动看完。没有键盘搜索，也没有按应用收起
- 已卸载和因包可见性看不到的应用用同一句「应用信息不可用」。账号数据仍按原包名保留
- 卸载前的中文应用名如果既不在分身名单的 `appName` 里、通道又没有解析出来，主应用只能靠包名、备注、账号和分身 id 找到它
- 备注名排序不是拼音序。`乙` 排在 `甲` 前面是码元顺序，不是字典错误
- 滚动位置在既有密码本重建时回到顶部。本功能的补名尽量只改标题文字，但挡不住原来的刷新重建
- Android 8–16 各品牌没有本功能的真机通过记录。HyperOS 上输入法与悬浮窗是否闪烁，只在真机上看
