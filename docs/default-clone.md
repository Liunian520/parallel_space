# 每个应用的默认分身（1.3.36）

未指定具体分身时，可以记住这个包要打开哪一份。点名打开的路径不看这条记录。

## 不改的启动

这些调用已经带了具体分身，继续打开那一份：

- 主屏、详情、私密空间里点某一张卡片或「打开」
- 桌面快捷方式和小组件（intent 里有 `clone_id`，userId 0 的旧快捷方式也算点名了第一份）
- 通知上原来的 PendingIntent

`VirtualEngine.launch` 仍使用调用方传入的 userId。方法通道没传 userId 时还是 0，和 1.3.35 一样，不会偷偷改成默认分身。

## 会看默认的启动

主屏在同一个包有多份分身时，菜单里有「按默认打开」。它走 `openPackage`：

- 用户明确设过默认，而且那份还在：打开它，名字用现在的自定义名
- 从没设过，且这个包只剩一份：打开那一份
- 从没设过，且有多份：弹出选择，不挑 userId 0，也不挑最近打开的
- 默认被删、不可用，或 userId 已经被另一份占用：删掉这条偏好，只要还剩任意一份就再问，不自动改开

选择器默认不记住。只有勾了「记住为默认」才写入。最近打开只更新活跃时间，不会变成默认。

## 身份

默认存在 `clone.defaults.v1`，值是 32 位小写十六进制 `launchKey`，同时写在那份分身的 `lk` 上。数字 userId 会在删除后被下一份复用，也会在「新建一个分身」恢复时变成另一个 id，所以不能拿来认人。

改名只改显示。标签每次从这份分身的自定义名读，没有自定义名时用原来的「应用名 / 应用名 分身N」。

升级后没有 `lk` 的旧分身不会被自动设成默认。

## 备份

配置备份仍是版本 3。多了一个可选的 `defaults`，里面只有 `pkg` 和 `lk`。旧版应用不认识这个字段，仍能读其余内容。旧备份没有这项。

恢复时只在本机那份分身已经有同一个 `lk` 时才把默认接回去。备份里的分身 JSON 即使带了 `lk`，也不会按 userId 写到本机另一份上。只有 `userId`、没有合法 `lk` 的条目直接丢掉。

定位里的「路线」是模拟轨迹，和这个无关，备份格式没改。

分身数据（`.aebak`）恢复：

- 覆盖原来的那一份：`lk` 还在，默认仍指向它
- 新建出来的 userId：不把默认搬过去。如果新分身带上了原来的 `lk`，清掉，避免两份共用
- 删掉之后又用同一个数字 id 建出来的分身：没有原来的 `lk`，不会成为默认

## 列举失败不能当成删除（1.3.37）

`listReport` 只有在引擎就绪、用户列表读全、并且每个 user 都列举成功时才把 `complete` 设为 true。Dart 看到 `complete != true` 或带有 `error`（通道失败、未就绪、`users_unknown`、`partial_users`、没有 complete 的旧列表）时，不调用会删除缺席分身的同步。因此刷新和覆盖恢复仍落在原来的那份对象上，`launchKey` 还在。

`complete=true` 且名单里至少有一台时，缺席的那一台会删除。1.3.43 起，空名单不再删除：BlackBox 在 Binder 失败时返回空列表而不抛错，不能把它当成「确认一台都没装」。磁盘上还有分身目录时，原生报告的 `complete` 也会改成 false。用户在界面里删除成功仍会删除，哪怕接下来停模拟定位时页面已经卸下。删除接口失败则不改名单。删掉之后同一个 userId 再出现，是新对象，没有原来的 `launchKey`，也不会变成默认。名单若已经被旧版本写空，能从数据目录、名称文件或快捷方式 extras 读回的身份会加回列表，不改那些目录里的数据；系统真清掉数据目录时无法恢复账号，也不会凭空造分身。

## 工作资料名单不能删除虚拟分身（1.3.38）

虚拟引擎不可用、工作资料状态又是 ready 时，刷新仍会读工作资料应用。那份名单没有虚拟 userId，解析后都是 0。1.3.37 仍拿它做删除同步，于是 userId 不是 0 的虚拟分身，以及工作资料里没有的 userId 0 分身，会连同 `launchKey` 和默认一起消失。

1.3.38 在这条路径上只更新能对上的名称、版本和冻结状态，不删除缺席分身，也不改默认。引擎恢复后，完整的虚拟名单仍然可以删除确认已经不在的分身。工作资料里卸载的应用，不会再靠这次刷新自动从卡片上消失，需要在应用里删除。点名打开、快捷方式、小组件和通知仍打开指定的那一份。

## 不做的事

不改登录隔离、通知隔离、相机 -1、边衬、桌面图标和只读密码工具箱。没有统一通知列表。
